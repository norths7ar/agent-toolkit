# DSH 插件前端设计约定

DSH 插件应融入宿主的设计语言，让用户在已有使用习惯中理解新能力。本文是各插件共同的设计与维护约定；具体产品流程和交互方案由各插件文档说明。

## 从宿主已有界面出发

新增或修改界面前，先阅读宿主同类组件、直接父容器及相关样式，确认组件是否向插件开放。优先复用宿主的工具栏操作、弹窗、表单、模型选择、正文渲染及状态反馈；无法直接复用时，沿用对应的视觉和交互模式。

字体、字号、颜色语义、圆角、间距、控件密度和图标体系跟随 DSH。参考其他项目时借鉴布局、样式归属和维护原则，不移植其配色、尺寸或组件风格。新增视觉模式应有具体用途，而不是为了让插件显得独特。

嵌入现有工具栏的入口，应与相邻操作使用一致的图标尺寸、点击区域、颜色和悬停反馈。图标按钮提供简短提示和可访问名称。主次操作、禁用和加载状态也应沿用宿主习惯。

## 样式与参数的归属

- 宿主已有的设计值以宿主组件和语义 token 为准，不在各插件中复制一套固定值。
- 插件跨页面、跨组件共用的扩展值集中在插件的公共样式入口；局部布局留在组件样式中。确实只服务一个布局的尺寸不必升级为全局 token。
- 同一视觉属性由明确的一层负责，避免组件参数、公共 CSS、局部 CSS 和内联样式相互覆盖。内联样式主要承载运行时计算的位置或尺寸。
- 插件样式限定作用域，避免改变宿主和其他插件的按钮、表单或正文。公共约定在本文维护，不为每个插件复制一份逐渐分歧的规范。

## 布局、宽度和滚动

先明确谁决定内容宽度、谁分配剩余高度、谁负责滚动。页面或弹窗容器决定主要阅读宽度，内部表单和列表继承可用宽度，正文跟随其所在表面；同一用途的页面和区块保持一致的对齐与尺寸规则，不由每个子组件单独设置固定宽度。

布局容器与可见表面各有职责：定位和占位由容器负责，背景、边框和阴影放在实际可见的表面上。透明区域不应无意遮挡相邻操作。弹窗需结合宿主的浮层、标题栏、焦点和关闭机制检查，不能只看中间的一块内容。

长内容和重复项目需要明确的长度控制方式，如折叠、分组、搜索或合理的滚动区域。根据阅读任务选择，不让列表随着使用无限铺开，也避免多个狭小的嵌套滚动区域。折叠后的标题应保留识别项目和判断状态所需的信息。

检查长模型名、长正文、代码块、窄窗口及展开／收起状态。保留布局需要的收缩与 overflow 边界，不靠固定窗口尺寸掩盖溢出。

## 信息、文案与交互状态

界面首先呈现用户能识别的名称、内容和操作。Provider ID、内部模型 ID 等实现标识只在区分来源或排查问题确有帮助时作为次要信息出现。

操作文案简短、自然，准确表达点击后的结果。分支、会话等技术机制不必全部写进按钮；必要说明放在附近的辅助文字或提示中。预览、保存、开始新会话等阶段应与实际行为一致，不能界面仍在预览，其他位置却已经发生未说明的正式变更。

生成中、完成、停止和失败应易于区分，并说明已有内容是否保留。后台更新不应无故改变用户的展开选择、焦点或阅读位置。正文按其内容类型呈现，Markdown、链接和代码块优先复用宿主渲染及交互能力。

## 在真实宿主中验证

视觉与交互变化需在 DSH 实际页面中检查。独立预览、截图局部或自动检查不能代替完整使用流程的体验确认。

按影响范围覆盖相邻操作、长内容、多项目、展开／收起、滚动、加载与错误状态，以及窄窗口和深色主题。检查键盘焦点、图标提示、关闭与返回后状态是否符合宿主习惯。

验证结果应区分源码核查、离线模拟和实际操作，明确哪些效果仍未确认。涉及真实模型请求或正式数据的操作沿用用户授权范围。
