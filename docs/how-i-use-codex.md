# 我怎么用 Codex，以及为什么要这么用

Codex 现名 ChatGPT，但是因为和网页聊天产品重名，我还是习惯保留 Codex 这个称呼。这一半面向编程工作者，另外一半对应的 ChatGPT Work 面向普通的非编程工作者，下文统一叫它 Codex。

我现在用 Codex 属于是相对定制化了，包括修改了底层的 base-instructions，自己写的SKILLS，也包括主流的 AGENTS.md 都改了。有些问题它们能解决，但是也有些还得盯着。

## 从 Claude Code 到 Codex

我接触 LLM 是从 GPT 开始的，但是接触 Agent 类产品，其实是从 Claude Code 开始的。

先说大模型。去年年底，我弃用了 GPT，因为它当时展现出了异常的啰嗦，于是我把主力模型迁到了 Claude。后面接触的也是 Claude Desktop 这一整个 GUI 软件，里面包括聊天、Work、Code 三大块。我没用过 CLI 的 CC，也不喜欢 CLI。

当时我的订阅是 20 刀的档位，不太够用。另一边的 Gemini 呢，模型降智，Antigravity 我也装不上，订阅档位还特别复杂。所以我又回过头开了个 20 刀的 GPT，装上 Codex，作为备用。

那时的工作流是 Codex 和 CC 分工，分别设置 `AGENTS.md` 和 `CLAUDE.md`，加上不同的设置。后来 Claude 被封了，我就转向 Codex 了。

这里先说一点：模型和 Harness 适配的优势在于，模型在训练过程中用的就是自家 Harness，所以使用起来效率会更高。不过，具体用起来，默认指令和默认行为仍然有很多让我受不了的地方。

## 为什么我要自己改指令

GPT 5.6 的时代，其实靠修改AGENTS.md，还能压住 5.6 Sol 的一些问题。但是用到 GPT-6 Astra 以后，加上提示词版本更新（可能是因为 OpenAI 自己觉得 Astra 够强应该更自由），模型越来越难约束，行为自由散漫，毫无水平可言。

我后面深入研究，发现 OpenAI 在 `config.toml` 里提供了 `model_instructions_file` 这个选项，可以指定基础指令文件。

于是我回过头去读了 base instructions，发现这个 Baseline 的质量就极其低下：一方面不符合我的需要，另一方面也有很多匪夷所思、不合逻辑的地方。我的解决方案就是 override 这个文件，然后迭代了两个版本。

这个修改是一步步来的，所以这里就只举几个例子。实际过程中它犯大大小小的蠢的地方多了去了，不胜枚举。

### 测试写了一大堆，产品还是不好用

首先是测试太多。模型写几百、几千项测试，却不告诉我测试了什么。那么这个数字是 1000，还是 100 万，都没意义。我的决策就是：从当天起，禁止模型新增任何测试。

而且 GPT 还有一个问题：它会反过来写测试，保证“某些被删除的东西没有继续存在”。这个行为应该一次性解决，而不是每个版本、每次测试，都重新验证一遍。这没意义。

前几天暴露出了一个更明显的问题。我有个编辑功能，使用过程是这样的：

1. 文件 A 原来是版本 1。
2. 我用编辑功能修改它，生成草稿版本 2。
3. 我又要求二次修改，执行的 Agent 却错误地在版本 1 上，生成了草稿版本 3。（预期行为是直接从草稿版本 2 进行二次修改，我允许它这么做）

结果，草稿 2 和草稿 3 在系统里成了两个独立的版本。我接受草稿 2 以后，系统根本不会判断 2 和 3 的修改互斥与否，而是直接告诉我：草稿 3 对应的原版已经被修改，不能采纳，不安全。

这里体现的问题，一个是测试不全面，另一个就是模型更倾向于防御性。它没有从产品经理的角度出发，而是在做一个得过且过的程序员：我自己不背锅就万事大吉，多的一点也不想。所以这次也推进我去自己的项目里，砍掉了大多数测试。

我对 GPT 的核心一问就是：**你怎么证明你理解了我的意图，而不是单纯按照我的字面意思去写了测试呢？**

我都可以隐约想起最最开始 写功能的时候 Agent 是怎么跟我保证的：两个草稿不会互相覆盖。但是然后呢？用户要继续修改，该怎么继续？接受前一个草稿以后，后一个草稿怎么办？

AI 根本没有从产品经理的角度思考问题，而是死板地 follow 了它自己在编程层面的防御性。不出错就皆大欢喜，至于用户拿到手的东西好不好用，它不 care，这不在评价标准里。

### 前端更是灾难性

GPT 写前端，尤其是配色，经常让我觉得它根本没有审美。比如我让它给 DeepSeek Harness 写个插件，现成的界面风格就在那里，照着做总该会吧？结果它连原有的美观风格都没沿用好，做出来的东西和宿主界面放在一起，怎么看都不协调。功能写出来了，就这么交差了。我当时人都要晕了。这也是“只管交付、不管使用”的一个很典型的体现。

### 版本都没对齐，先枚举 32 种补丁组合

还有另一个问题。我安利给大家的 OpenCodex 代理聚合插件，我本机装的是 2.88，而我做修改、提 PR 的源码版本是 2.91。

当时我说，如果我的 PR 迟迟不通过，那就先把补丁打到本地吧。然后 AI 跟个弱智一样，没有提醒我版本不一致的问题，而是自己直接尝试重新做降级补丁。甚至因为我有 5 个补丁，它枚举了 32 种情况，以确保补丁不会互相影响。

我需要它提前警告我版本不一致可能装不上，应该由我做决策，结果它的行为是自作主张的去浪费我的token做没意义的事情。

这里我的 Instruction 已经写到位了。我不可能无限制地失败一次就加一句话，那样最后就没有 Context 留给我的正文了。基础指令需要让它理解该怎么判断问题，而不是让我提前穷举它每一种可能犯蠢的方式。

## 基础指令、AGENTS.md 和 Skills 怎么分工

调整到现在，我把这些内容分开放。

[`astra-base-instructions`](../instructions/base-instructions/astra-base-instructions.md) 负责约束整体的工作方式和风格，包括理解我的意图、遵守已经接受的决定、从产品使用的角度考虑结果，以及减少那些无意义的防御性行为。

传统的 [`AGENTS.md`](../instructions/AGENTS.md) 则负责记录我本地电脑和工作区相关的东西。例如用什么 shell、Python 环境怎么管理、项目放在哪里、Git 推送到哪些远端。具体项目还有自己的约定，进入项目以后再读项目里的指令。

Skills 则放特定任务需要的方法。处理 PowerShell 调用、执行 Git 写操作、委派子代理、迁移旧实现、独立审查、写文档，这些场景需要的东西不一样，我把它们拆成各自的 Skill。

这样我可以分别调整：整体协作方式有问题，就改基础指令；本机环境和项目约定有变化，就改 `AGENTS.md`；某一类任务反复出问题，就整理对应的 Skill。

## 我现在用的几项 Skills

### powershell-safe-invocation：先把 Windows 上的命令执行明白

我在 Windows 上使用 Codex，所以首先得处理 PowerShell。这里我指定使用 PowerShell 7，也就是 `pwsh.exe`；`powershell.exe` 对应的是 Windows PowerShell 5.1，两者可以并存，装了 7 也不代表调用 `powershell.exe` 就会变成新版。

简单说，5.1 是基于旧 .NET Framework 的 Windows 版本，7 则基于现代 .NET，支持 Windows、Linux 和 macOS。对我这种使用场景，比较实在的改进是文本输出默认采用无 BOM 的 UTF-8，跟现代开发工具对接更方便；7.3 起还改进了调用外部程序时的参数传递，对参数里的引号、空字符串处理得更好。这些正好都是 Agent 执行命令时容易踩坑的地方。具体差异可以看[微软的说明](https://learn.microsoft.com/en-us/powershell/scripting/whats-new/differences-from-windows-powershell)。

所以我会明确要求它用 `pwsh.exe`，别一边写着新版的命令，一边又跑进 5.1 里执行。

[`powershell-safe-invocation`](../skills/powershell-safe-invocation/SKILL.md) 处理的是实际调用时的细节：不要把 Bash 的语法直接搬进 PowerShell，不要混用不同 shell 的环境变量和转义方式，处理好带空格的路径、引号和原生程序参数。

例如，调用程序时应该把可执行文件和参数分开传，而不是先拼出一整个命令字符串，再套几层 shell 去解释。需要判断执行结果时，也要分清原生程序的退出码和 PowerShell cmdlet 的错误处理，不能混着用。

它还包括文件操作和后台进程的约定，以及出错之后该怎么处理。这些细节很基础，但 Agent 连命令都没执行对，后面的工作就无从谈起。

### git-safe-workflow：别为了绕过报错乱改环境

[`git-safe-workflow`](../skills/git-safe-workflow/SKILL.md) 其实出现得很自然，和 Codex 在 Windows 沙箱环境下的权限问题有关，也包括其他 Git 流程上的问题。

例如，沙箱里访问不了凭据或者签名密钥，就应该按权限流程到沙箱外重试，而不是擅自关闭提交签名，更不是直接修改 `.git` 或项目目录的 ACL。`gh` 的认证失败也一样，先处理执行环境的问题，不要上来就折腾重新登录。

另外，我有些仓库会同时推送到 GitHub 和私有 NAS 上的 Gitea，所以它需要读项目的推送约定，分别推送、分别确认结果。一个成功、一个失败，就明确告诉我，不能笼统地说“推送完成”。提交、推送、打 tag 和发 release 的授权也各有各的边界。

### fidelity-aware-implementation：让你照着做，就别自己乱搞

[`fidelity-aware-implementation`](../skills/fidelity-aware-implementation/SKILL.md) 的起因，是模型之前不止一次在应该复制、甚至照抄的情况下，跑去自己乱写实现，给我人都气晕了。所以我加了这一条，要求它 follow 我的指令，而不是自己乱搞。

我让它复制一份实现，它不能擅自理解成“看懂大意以后重新写一个差不多的”。这个 Skill 要求它去读旧实现、调用方和配置，把原有行为当作任务的一部分。**我没有在需求里重新列出每一项旧功能，不代表那些功能可以随便丢。**

实现的时候，要知道哪些能力保留了，哪些是我明确要求修改或删除的，哪些还没有对应上。完成以后，也得从旧实现往新实现追，看看入口、条件和效果还在不在。

### adversarial-fidelity-review：让独立代理检查它到底丢了什么

[`adversarial-fidelity-review`](../skills/adversarial-fidelity-review/SKILL.md) 是在我的 L4D2 AstRedux 项目里形成的。改插件的过程中，我观察到模型有可能不汇报一些隐性的、意料之外的功能丢失、配置改变等问题。所以我单独配置了这个 Skill，要求子代理去对抗父代理，给我汇报。

它和前一个 Skill 配合：前一个要求实现时保留该保留的东西，这一个要求实现结束后，再由没有参与实现的独立代理检查一遍。

审查代理需要拿到我的原始要求、后续修正，以及新旧实现，自己去读、自己去比较。不能只看主代理写的总结，然后沿着“功能已经全部保留”的说法继续往下走。

它要查的是原来的功能分支还有没有，默认配置有没有变，接口和扩展点是否还有效，某个开关是否表面保留了但实际不起作用，某些状态下的行为是不是悄悄没了。发现问题，就给出位置、触发条件和对用户的影响。

我需要它把主代理没交代的损失找出来，而不是让主代理自己检查自己，最后再跟我说一次“一切正常”。

### delegation-router：主代理要会分工，也要负责验收

[`delegation-router`](../skills/delegation-router/SKILL.md) 是要求主代理拉起子代理的 Skill。这里我留了一些判断的自由度，让它根据任务决定怎么分工。

委派时要把目标、上下文、相关路径、允许修改的范围和验收要求交代清楚。多个代理同时工作，要分开写入范围，别几个人一起改同一个文件，最后互相覆盖。能并行的并行，有依赖关系的就按顺序来。

主代理还得看实际结果，验收子代理交回来的东西，处理冲突。子代理说做完了，不等于可以原封不动地把这句话转述给我。最终结果仍然由主代理负责。

这里也涉及上下文和成本。OpenAI 对缓存超过一定额度之后的 credits 消耗计算会提高，所以 GPT-6 Astra、GPT-6.1 Sol 之类的模型，可以调高数值享受百万上下文，但也有代价。子代理怎么用、给多少上下文，都是工作流里需要考虑的事情。

### writing-fidelity：写文档也别擅自改我的意思

[`writing-fidelity`](../skills/writing-fidelity/SKILL.md) 是另一项相似的 Skill，用于写报告、写文档，以及修改和审阅文字。我要求它减少废话，减少无意义的防御，聚焦问题。

写作时也会发生和实现时类似的问题：模型没有沿着我的意思往下写，而是自己加一些我没说过的前提、反对意见或者限制，然后花一大段去回应它自己虚构出来的问题。

所以这个 Skill 要求它先理解我到底在说什么，保留我的原意，再根据文档的用途组织信息。相关的内容放在一起，原因、做法和结果讲清楚，不要用一堆零碎标题和重复结论把简单的事情写复杂。

## MCP 和多模型组合，我也折腾过

除了指令和 Skills，我也试过通过 MCP 组合模型能力。

我试过本地部署小模型。之前玩初代 QQ 机器人的时候，也试过写一套让 MiMo 做 DeepSeek 的眼睛的东西。但本地模型小且不实用，而 MiMo 做 DS 的眼睛又有点复杂，上下游传递消息还得考虑可靠性。

后来我就只考虑一个模型解决问题了，不论是单 MiMo 还是单 DS，之前为这种分工做的 MCP 也就没意义了。

另外也有本地模型的 MCP，包括识图和翻译。其中前者和 MiMo 识图一起退役了，而后者呢，翻译模型太小、不知道人名等专用词，也同样不好用。

这部分也构成了我的 workflow 演变：试过把能力拆给不同模型，再把它们接起来；用下来发现有些连接本身就带来了额外的问题，最后又收回到一个模型解决。

## 写了这些，仍然得时刻约束 AI

这些指令和 Skills 都有对应的问题来源，但它们还远没有做到完美。前面 OpenCodex 补丁的例子就是如此：Instruction 已经写到位了，它还是能绕开应该先处理的问题，自己折腾一大圈。所以我只能说，就是得时刻约束 AI。

另外我观察到的一点是，至少在 Codex 里，压缩上下文之后，Skill 疑似被卸载，base instructions 也忘得差不多了，行事风格会大幅度偏向原版。所以必要的时候，我会要求它重读指令，以确保服从。

我也不可能每失败一次，就再往指令里加一句禁止事项。上下文不是无限的，我还需要留空间给真正的任务。现在这套配置，就是我在实际使用中不断调整出来的工作方式：让它执行得明白，保留该保留的东西，检查真实结果。

而我用来判断它有没有做好工作的，仍然是前面那个问题：你到底理解了我的意图没有？最后交到我手里的东西，到底好不好用？
